The free, open base of NovaByte OS.

NovaByte Open Source Project (NBOSP) is a browser-based operating system foundation you run, fork, and build on top of. No edition system, no update pipeline, no bloat — just a minimal OS that gets out of your way.

Who it's for

Built for developers, not everyone.

NBOSP is heavily developer and engineer focused. Expect fewer features than the full product — that's not a bug, it's the point.

NBOSP is the actual foundation NovaByte built its own closed-source OS on top of — not a stripped-down demo released alongside it. NovaByte took this exact codebase, added an update system, Nova Core Services, and a full set of proprietary apps, and shipped that as v3. From here on, the two app lines are maintained separately: NBOSP's apps stay feature-frozen and get bug and security fixes only, while NovaByte's own apps keep gaining features on their own track. Basic security — rate limiting, CSRF protection, and security headers — is built into NBOSP itself, not bolted on by whoever forks it.

NBOSP is

  • A minimal, fast, stock OS with basic security built in
  • Apache 2.0 licensed — copy, modify, fork, sell, redistribute
  • Feature-frozen apps that keep getting bug and security fixes
  • A skeleton meant to be forked and built on top of
  • Actively maintained — fixes ship faster than the full product

NBOSP is not

  • A polished, consumer-ready daily driver
  • Getting new user-facing features (Settings and dev apps excepted)
  • Bundled with an update pipeline or telemetry of any kind
  • A competitor to the full closed-source NovaByte OS release
  • A finished product — read that twice before you file a feature request

Why Settings is the one exception: it isn't really an app — it's the configuration layer for the whole OS, controlling the visual identity (themes, accents, layout) of every window, not just its own. Because it affects how the OS looks and behaves at the system level, it keeps receiving new options and visual updates as NBOSP evolves, same as the developer-only apps below.

Questions

Before you file an issue, check here.

Why does NBOSP need npm start to run nw . instead of a normal Node server?

NBOSP ships as an NW.js (Node-WebKit) app, not a browser-hosted page — package.json's start script is nw ., which launches the bundled Chromium-based runtime with full Node access in the window context. A prestart hook runs scripts/bootstrap.js first, which checks if node_modules is missing or stale against package-lock.json and runs the install for you.

Do I need to trust a certificate every time I launch it?

No — only once. On first launch NBOSP generates a local HTTPS certificate and CA under the hood; your OS prompts you to trust it a single time, and every launch after that is warning-free HTTPS.

What actually happens when I install a .novaapp package?

Every file inside the package is run through the built-in scanner before any trust or integrity checks happen — it's a heuristic, client-side gate (not a full antivirus) that checks for disguised executables, embedded scripts in previewed files (SVG/HTML/Markdown), obfuscated code patterns, and high-entropy content masquerading as text. A flagged file blocks the install outright with no override. Separately, packages are checked against the built-in trust store for Ed25519 signatures: Verified means it was signed with NovaByte's own private key, held offline and not distributed to developers — so a self-signed package, however legitimate, will always show as Unverified. There's no automated review queue yet either; NovaByte reviews submissions for that Verified key manually, offline.

Is Developer Mode safe to leave on?

Not by default — no. Apps like Console (arbitrary JS in the full OS context, no sandboxing) and Modules (hot-reload with the ability to execute arbitrary module paths at runtime) skip the confirmation prompts the standard app set has. Treat Developer Mode as a debugging posture, not a daily-driver setting.

Why does the App Manager have no update system?

It's intentional, per the app's own scope: install by drag-and-drop or URL, pin/unpin, enable/disable, auto-launch on boot — no app store or catalogue, no update management. NBOSP's apps are feature-frozen by design; they get bug and security fixes, not new capability surface.

What's the difference between NBOSP and the full NovaByte OS release (v1/v2/v3)?

NBOSP (this repo, under /NBOSP) is the Apache 2.0 foundation — minimal, feature-frozen apps, no update pipeline, no telemetry, meant to be forked. The versioned v1/, v2/, v3/ releases are the full closed-source product built on top of it, distributed as a compiled executable via Releases only.

If NovaByte fixes something in NBOSP, do I get the fix automatically?

No — NBOSP doesn't use the built-in System Updates app at all; that's a v3-only, closed-source component. If a fix lands in this upstream repo, it stays there until whoever forked or packaged your copy pulls the change, repackages it, and cuts their own release — you then re-clone or re-download from them. There's no push mechanism, which is also why NBOSP ships no telemetry.

Get started

Running NBOSP takes one command.

npm start runs prestart first, which bootstraps a fresh clone automatically — nothing to configure by hand before the window opens.

1
Clone and start

npm start triggers a prestart hook (scripts/bootstrap.js) before nw . ever runs. It checks for node_modules and installs dependencies automatically if they're missing — first run or after a clean, no manual npm install step either way.

2
Env and certs, generated for you

Bootstrap also writes a .env with a random SESSION_SECRET and sane defaults, then generates a local HTTPS certificate and CA. Your OS prompts you to trust it once — accept, and every launch after that opens over HTTPS with no browser warning.

3
The window opens itself

No manual browser navigation — NW.js spawns the app window directly once the server's listening on 127.0.0.1:3003 (HTTPS if certs are present). Want verbose logs while you work? npm run dev runs the same thing with --enable-logging=stderr --v=1.

4
Build on it

Named extension points, not guesswork: new API endpoint → security/routes.js or email/index.js. New proxy → server/proxies.js. New middleware or rate-limit tier → server/middleware.js. Every module is independent — no global state, no tight coupling to route around.
